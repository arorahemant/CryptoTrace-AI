# Tracing engine

`TraceEngine` uses bounded BFS with max hops, max transactions, amount, direction, chain, and time-window controls. Historical demo windows anchor to the newest available record; timestamps are never shifted. Visited addresses and transfer identities prevent cycles and duplicate work. Provider exceptions and malformed transaction records are skipped rather than turned into fabricated transactions; the result includes provider-error counters and a `trace_status`/`trace_warning` pair so partial traces can be surfaced to investigators.

Ethereum uses a separate bounded traversal through the explicit Alchemy adapter: 2 hops, 100 transfers, 200 requests including retries, a shared 10-second deadline, sequential I/O and a pinned finalized historical interval. Receipt reconciliation and historical decimals precede exact accounting. Pagination exhaustion is distinct from partial coverage. Errors, metadata gaps and hop/transfer boundaries remain visible, and a frontier is not a proven destination. Demo traversal is unchanged. See [Blockchain data](BLOCKCHAIN_DATA.md).
