# Security

The declared dependency set pins bcrypt 4.0.1 for Passlib 1.7.4 compatibility. A clean backend environment was rebuilt with bcrypt 4.0.1; startup, authentication, and the complete regression suite passed without the prior version-detection warning.

Bearer JWTs protect case routes. A production configuration (`DEMO_MODE=false`) fails closed unless `SECRET_KEY` is injected with a non-empty random value of at least 32 characters; no reusable signing secret is embedded in source. Demo mode generates an ephemeral process key when no key is configured, preserving local usability without creating a production fallback. Known demo accounts are seeded only when `DEMO_MODE=true`; production accounts must be provisioned through a controlled operator workflow. Login failures are throttled in-process (five failures per source IP per 60 seconds); production should move this control to a shared gateway/store. CORS uses an exact, comma-separated `CORS_ORIGINS` allowlist; demo mode defaults to the two local frontend origins, while production must provide its deployed frontend/native origin(s). Wildcard origins are rejected because credentials are enabled. Provider/LLM credentials remain backend-only.

Case routes resolve one active user through a single request dependency and pass that identity to the case authorization check. Investigators access owned cases; supervisors/admins review cases. Unknown and unauthorized IDs return 404 to reduce enumeration. Investigation execution locks the case, reuses one persisted snapshot for repeated requests, and relies on request-transaction rollback for retry after persistence failure. Evidence links are validated against the requested case, and unsupported AI identity/off-case/future-fact requests are refused before a configured LLM is called. Key case lifecycle actions—case creation/view, investigation completion, evidence save, and report generation—are persisted in AuditLog records, and `GET /cases/{case_id}/audit` only returns events whose case reference matches the authorized case; stored IP addresses are not exposed by that endpoint.

The authorized case-detail response exposes a minimum accountability projection derived from the persisted case owner and user record. It includes display name and role plus case-scoped timestamps, but excludes investigator email, username, credentials, token data, IP addresses, and unrelated activity. The current schema does not support reassignment history and the API says so explicitly.

No live blockchain provider or PostgreSQL runtime has been verified in this pass. The in-process login throttle and SQLite demo fallback are prototype controls that require deployment-specific hardening before production use. The database selector now fails closed when `DEMO_MODE=false` is combined with a SQLite URL or `USE_SQLITE=true`; it cannot silently convert a production configuration into the demo database.
